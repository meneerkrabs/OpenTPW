## Online button labels fit their buttons (October 17, 2026)

On the online screens some labels were drawn one character per line: the outbox's three bulk buttons ("Mark all for sending", "Mark all for deletion", "Unmark all"), the dialogs' 83 x 83 close button ("Back") and the news tab "System News". Since the text block placement of the same day the overflow also centred and spilled upward over the panel. Cause: the label fitting (`[EXT:fit-button-text]`) wrapped into the box when nothing fit on one line, and the text library's breaker cuts an overlong word between characters, so a box of 24 to 50 pixels gave one letter per line. Original, read statically in tp.exe (nothing run): the table builder (0x65fd58) creates these controls as button objects (0x6688b3) from a rectangle, style and id only, with no text field, font slot or wrap flag; a control's text is a separate text control (0x48f830) whose wrap byte (+0xda) is off by default, so it draws one line into a bitmap the size of its box, which cuts off both ends. The original's bulk and close buttons are art buttons without these labels; the labels are OpenTPW's own text ([EXT:ONLINE-UI]).

The fix keeps the existing extension labels. The fitting now also tries the body fonts below the family's smallest size, then wraps at spaces (never inside a word) in the largest size that fits the box height, and only for a box too small for that shows the smallest size on one line. The outbox's three bulk buttons carry their label as a wrapped caption under the button, because the label cannot fit a 96 pixel button at any size. Checked in silent offscreen front-end smoke captures in English, Dutch and Korean (news, outbox): no label overflows or breaks inside a word. New tests cover `UiTextFit.ChooseWrapped`. Not changed: clipping an overflowing block to its box as the original's bitmap does (the batch has no clip rectangle), and a stale Dutch front-end smoke assertion (the injected V key) when the smoke is started with `--language Dutch`.
