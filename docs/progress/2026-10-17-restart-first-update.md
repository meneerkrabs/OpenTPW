## The first update after a restart save, and the corpus economy import (October 17, 2026)

A follow-up to the restart.INTS import: what tp.exe does with the restart saves' unplayed calendar once the park runs.

- **First update (new `APPROX:ECON-060`)**: the calendar constructor `0x4F7E80` stores day cache -1, the calendar loader `0x4F7F30` restores the saved caches unchecked, and the update `0x4F8260` posts a day message (`0x40F4C0`) whenever the computed day differs from the cache (`0x4F8321`), then stores the caches (`0x4F8538`). So the first update after loading a restart save, whose calendar still holds day -1, posts a day message whatever the date: every object's six rings roll from head -1 to 0 (`0x4DD320`) and the day listeners run. A new park behaves the same: the world init `0x5156A0` (called by the level start `0x407E00` before any quick save is loaded) syncs only the month and year caches to turn 0 (`0x4D7AF0` → `0x4F85A0`), so on PC a new park's first update posts a day message but no year message (the Mac oracle's constructed calendar also posted a year message). OpenTPW starts synchronised and posts neither; that difference was only described in a comment at `ParkCalendar.Update` and is now a register ID with the evidence needed to close it.
- **Corpus test**: `OriginalSaveCorpusTests` now runs `OriginalEconomyImport.Apply` on all eleven private saves, the four restart saves included, and checks the imported object and fixed-item counts and that each save's calendar agrees with its turn.
- **Docs**: docs/TPWS-PAYLOAD.md drops the stale note that the block split and the thing walk had not run on the private saves (the note also split the table), docs/reverse/ORACLE.md qualifies "only a new park shows it" for PC and the restart saves, and docs/SAVE-THINGS.md points to ECON-060.
