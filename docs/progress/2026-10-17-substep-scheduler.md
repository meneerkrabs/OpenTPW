## The original's substep scheduler runs the scripts, the bump module and the tour cars (October 17, 2026)

DET-013 is narrowed to what is left. tp.exe's main loop (`0x54F4BF`) runs a 31 ms substep, and OpenTPW now runs what the substep runs in the original's order, derived from the park's own tick count (`SimulationSubstep`: substep *n* ends in the first 60 Hz tick whose end is at or past *n* x 31 ms; the turn counter is the substep counter divided by eight, exactly). Read in tp.exe via REA:

- **The script pass** (`0x5516B0`, called at `0x54F56B`): a pass counter (`0x8791A4`) rises, then the script list is walked, and a script runs a slice only when `(script id +8 xor pass counter) & 7 == 0` or its TURBO byte `+0xB8` is nonzero (`0x5516E1..0x5516F6`): one slice per eight passes (248 ms), on the pass its id selects. A new script is linked at the list's head (`0x5599D3`, `0x5588C0`), so the pass runs **newest first**; the script ids are a never-reused counter (`0x8791A8`, 1 at the start, `0x558C0D`) and so the creation order. `RideScriptWorld.RunPass` and `RideVM.StepSubstep` are that pass; every script's clock gains 31 ms per pass, slice or not, so a WAIT wakes on the first slice after its time. The pass counter restarts at 0 when a level loads and is not in the original's save; OpenTPW's park save carries it (optional `RideScriptWorldSnapshot.PassCounter`, 0 when absent, validated non-negative) so a resumed park continues exactly.
- **The bump module** (`0x546C80`, `0x54F55F`) ticks once per substep before the scripts; **the tour cars** (`0x55ABF0`) only on even substeps (`test al,1` of the substep counter `0x877D34`, `0x54F5D7`), after the scripts; the park turn follows when the counter's low three bits are clear (`0x54F668`). The renderers' interpolation fractions (the bump and tour remainders) are now derived from the clock, not accumulated.
- **A paused park runs no substep** (`0x54F4D4`: the body is skipped while the pause flag `0x7A1A8C` bit 0 is set), so a paused park's scripts and rides stand still, as its calendar does; before, the scripts went on.
- **A lost park** (world state 4) still runs the turn's tail: `0x516395` jumps to the gate retry, and the arrival update (`0x4D7B20` -> `0x4CF3E0`) tests no world state of its own, so the turn's tail runs in every state (the group is 0 there, `0x4CF5B0`, but the bus still comes and goes). The old code skipped it.
- **The weather** is stepped once per swept turn, by its thing in the walk; the second call at the end of `SimulateSweptTurn` was a no-op (`ParkWeather.AdvanceTo` steps while `lastTurn < turn`) and is gone. A lost park's weather thing is not walked, so its weather stands still, as the original's.
- **The advisor draws nothing (DET-015).** The one world draw of its update (`0x59A550`) is the mode-3 pick (`0x59A7AC`); the mode word (descriptor `+0x2C`, `0x59C490`) is 2, "previous + 1" (`0x59A796`), in all 351 rows that the initializer `0x5A0A50` fills (`tpw_exe_tables.py` now fails if any row differs), so the branch is unreachable and the advisor stays off the stream for good.

**Pinned digest moves** (docs/DETERMINISM.md): the fixed synthetic run `0xE48128553808938B` -> `0xA91A607272718E93` (schema 21 stays). Cause: the fixture runs Level's substeps, so the shop's and the dice scripts take one slice per eight substeps in the original's pass order instead of one on every tick, and their draws, waits and every guest interaction after them move. The script pass counter joins the canonical hash once a pass has run, so a world that never ran one keeps its other pins.

**Saves**: one optional field, `PassCounter`, in the script world's snapshot; an older save loads and the counter restarts at 0, as an original save's does.

Still open (DET-013): a script created with an explicit seed keeps a private generator; the ids and pass phase of an imported original save's scripts are OpenTPW's creation order (the saved script ids and states are not imported); the ride visitor protocol's host step, the coasters and the animators stay per 60 Hz tick, and the effects system (`0x520130`) and the second even-substep system (`0x475360`) are not modelled. ECON-001's catch-up cap stays `EXT:fixed-catch-up-cap`.
