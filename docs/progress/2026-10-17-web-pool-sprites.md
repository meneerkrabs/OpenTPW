## The pools sprites reach the browser on demand (October 17, 2026)

The Blender sprites of the pools extension (the 2x land guests and the swimwear sets, 8.84 MB) now ship in the browser too, without growing the startup download. `content/pools/esprites.manifest.json` pins the path, size and SHA-256 of every sprite file (`tools/pools/sprite_manifest.py`, run by `build-content.sh`; a test fails when it and the files disagree) and is the only part embedded in the web assembly (about 7 KB). The web project publishes the files as static files below `pools-sprites/`, the server image now copies `content/pools` and `content/mods` into its web build, and after the start `main.js` fetches them in the background with three requests at a time: the swim sets (6.56 MB) whenever the extension is on, the land sets only with the pool guest art switch on. `Program.AddPoolSpriteFile` keeps a file only when path, size and hash are pinned (traversal, unknown paths, a wrong size or hash are refused). A set is used only when every file of it is in: a park that loads earlier keeps the game's guests, swimmers use the kid sprite and get their own renderer mid-level once the swim sets are complete, and offline or a 404 leaves the fallbacks with one console line and no retries. The desktop is unchanged. Checked in Chrome against a locally published interpreter build with the pools extension on: all 48 files were fetched and stored (sizes as pinned) within seconds of the lobby, a jungle park then used the extension's 2x land guests, and with the files blocked the page logged one line and the park kept the game's guests. The startup download grew by about 11 KB Brotli; swimmers switching to their sets mid-level were not observed in a browser.

Review follow-up. The server (`WebClient.cs`) maps `.esp` and `.tpc` to `application/octet-stream`: .NET knows neither, `ServeUnknownFileTypes` is off, so the sprite files were a 404 on the server image (play.opentpw.io) until now; the CI server-image smoke fetches three sprites from the running image and checks their size and SHA-256 against the manifest. The server image also copies `content/pools` and `content/mods` into its web build, which it did not before: the deployed page therefore **never had** the pools objects (about 88 KB Brotli) or the data mods OpenTPW ships, including `opentpw.tpi-rides` (about 31 KB), that the browser build was meant to embed; the production page grows by about that much, a fix of that older bug and not part of the sprite delivery. The swim sets are no longer decoded twice nor eagerly: the desktop decodes them on a worker only for a park with pool water (or from its first painted pool cell), the browser when the swimmer renderer is created. The bottom-anchored swim frames use one lift per animation (the largest rows below the hotspot) so they do not jump between frames, and a lounger's lying step rests on its cushion (0.68 engine units). The page reads a sprite body as a bounded stream, tells the game once when no sets will arrive (no manifest, nothing planned, a failure), and `main.js` no longer lets a link seed `/config/mods.json`.
