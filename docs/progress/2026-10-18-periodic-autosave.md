## A park in play autosaves every five minutes into its own slot, and a crash offers "Continue autosave" (October 18, 2026)

A browser player's game crashed and the park was lost: the only automatic save was the checkpoint of Exit To Lobby. A park in play is now also saved on a timer (`[EXT:periodic-autosave]`, user-approved 2026-10-18).

- **Original**: checked statically in tp.exe (REA): the park-save writer `0x5AC610` is called by the park state machine `0x54E360` in its leave state (0xB, not the online visit), by the quick-save command `0x40BF90` and by a save-screen action `0x49E9B0`; the running state reaches state 0xB only on the exit request. No timer calls it, so the original's `autosave.TPWS` is written on leaving a park, not periodically (an indirect timer callback cannot be ruled out from the executable alone). The periodic save is OpenTPW's own.
- **When**: every 5 minutes of play time (frames that simulate; a pause, the map window, a texture-pack download or a park build counts nothing, a frame counts at most 0.25 s) in a Theme Park World Full Simulation or Instant Action park the player owns; never in a read-only visit, the front end, the sandbox or Theme Park Inc. A refused capture (the advisor speaking, a staff member in hand, any capture refusal) is retried after 15 seconds, and after 8 refusals in a row the autosave waits a full interval; a failed write is retried the same way.
- **Where**: `save/opentpw-<theme>-autosave-world.json`, its own slot per theme (desktop and the browser's `/save`, which the page mirrors to IndexedDB). It never touches the manual save or the Exit To Lobby checkpoint, and does not flush the ticket progress or retire the park. The write is the manual save's atomic one (`ParkResumeSaveFile.SaveBytes`: temporary file, flush, move), and the next write removes a temporary file a dead process left behind.
- **No hitch**: the capture is one frame between ticks (the park must be consistent): 3.3 ms for the real park of the park-resume smoke and 1.3 ms for 1500 guests; the validation, the JSON serialization (`SlicedJsonSerializer`, 2 ms slices per frame, the same bytes as the manual save's serializer) and the file write (worker thread on the desktop, inline in the browser) are moved out of that frame. The asset manifest is hashed once per park and kept (hashing it was most of a capture: 183 ms for the first capture). Measurements are in PARK-SAVES.md.
- **Recovery**: the theme menu's automatic entry offers "Continue autosave" when the autosave is newer than the Exit To Lobby checkpoint and than the manual save (`AutomaticThemeContinuation.Newest`); the label is translated into the nine languages.
- **Option**: OpenTPW page of the options, "Autosave: On/Off" (`GameOptions.Autosave`, on by default, translated like the other rows); old options files read as on.
- **Tests**: `PeriodicAutosaveTests` cover the interval and the play-time counting (pause, frame spikes), the refusal and retry (and the backoff), a busy and a failing write, the atomic write (a read-only folder leaves the previous bytes, a stale temporary file is removed, the manual and checkpoint slots are untouched), the sliced serializer's bytes and its contract guard over every snapshot type, the validation refusing a snapshot, the recovery choice and the menu entry, the options row and file, the nine translations, and a real-level capture that leaves the state hash and the random streams unchanged and a captured snapshot unchanged while the park runs on. The park-resume smoke takes the autosave of its real park and checks the same things.

**Determinism pins**: none moves. The autosave draws from no random stream and reads the park only between ticks; `PeriodicAutosaveTests` compare the state hash, which covers every random stream, before and after repeated captures. The full suite with game data and the smokes pass (see the pull request).
