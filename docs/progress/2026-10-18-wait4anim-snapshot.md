## Parks started from an original save write their restart snapshot and autosave again (October 18, 2026)

The native front-end and Jungle smokes logged "Restart snapshot not written (Script 4 WAIT4ANIM deadline -1 is not finite and non-negative.)". The cause was not an animation opcode: the import of an original save's script run state (`RideVM.ImportSavedRunState`, the loader at tp.exe 0x5597A0 reads the WAIT4ANIM deadline at script +164) turned a saved deadline that lies behind the saved clock into -1 as a "past" stand-in, and the snapshot validation rejects negative deadlines. A finished animation wait leaves its deadline in place until the script runs WAIT4ANIM again; of the four shipped saves and the 11 corpus saves only Jungle's shipped Easymode save holds such a deadline (1 of its 14 script records), so every park started from it (Instant Action Jungle, the front end's Jungle, a Jungle Load Park reference) failed to capture its script world. That made Restart Park unavailable there, and the periodic autosave and the manual park-resume capture use the same script-world snapshot and validation, so they failed in those parks too.

A deadline that is not ahead of the saved clock now imports as 0 (none). WAIT4ANIM (0x5538EB) treats the two alike: a zero or reached deadline continues and leaves the deadline cleared, so behaviour does not change. The snapshot format and validation are unchanged, and old saves load as before. No determinism pin moves; the hashed script state of a park started from that save does change (`RideVM` hashes `Wait4AnimDeadline`: 0 instead of -1 until the script next runs an animation opcode), which no pinned run covers. Regression tests: `SavedRunStateTests.APastWait4AnimDeadlineImportsAsNoneAndTheScriptSnapshotStaysValid` and, with game data, `OriginalParkScriptSnapshotTests.AJungleParkStartedFromItsShippedSaveCapturesItsScriptWorld`. tp.exe (byte-exact): WAIT4ANIM at 0x5538EB returns at once for a zero deadline and writes 0 once the clock reaches it; every other access to +0xA4 in the VM (0x552B14, 0x552BFF, 0x552D9F, 0x552FE5, 0x5531F9, 0x553388, 0x55347F, 0x55368D) writes it without reading the old value, and the save loader 0x5597A0 reads the record raw.
