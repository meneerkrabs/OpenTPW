## The browser's AudioMixer memory does not grow per park visit (October 21, 2026)

The browser memory notes reported the `AudioMixer` root growing by about 4.6 MB per park visit (18.7 -> 23.3 MB between two lobbies). Six visits on the published AOT build show it does not grow: the 4.6 MB were a sentence's sample decode caught in flight (the lobby music's long segments are decoded a few MPEG frames per browser frame, and until a decode ends it holds its MPEG input and its doubling PCM buffer), and the root also counted the file system's 11.3 MB of cached archive members, which the sound categories reach. Sampled after the decodes end, the root is 20.0-20.2 MB in every lobby.

The `switch` scenario now waits for no sound decode to be in flight before each point, takes `--visits <n>` for longer runs, and reports what the mixer reaches by the field holding it (`PerfAudioBytes`, `soundDecodesInFlight`, `soundVoices`, `soundVoiceSampleBytes`). The root walks no longer read `ConditionalWeakTable` entries, which crashed them in the AOT runtime once a key was collected. `GameAudio.Counts` gives the sound system's holdings, and the with-data test `AudioParkVisitTests` checks that five lobby-park-lobby visits leave the same holdings as the first. Details: docs/BROWSER-PERFORMANCE.md, "The AudioMixer root across visits".
