## A texture per park visit, and the managed step after the first visit (October 21, 2026)

Every park visit left one texture behind for the session: the blueprint markers' area texture (the coaster tool's yellow-and-black placement square, made from bytes) was not released when the park's markers were deleted. It now goes with them, and in the browser the textures held stay at 306 in Jungle and 277 in the lobby over six visits (they grew by one per visit). The texture-pack list of `.wct` textures, which kept a dead weak reference for every texture a park had loaded, is now pruned as it grows.

The native front-end smoke test checks that the textures not loaded by path are as many in the lobby after each park as before the first (the type signs kept for the session left out), and names the file and line of any texture left; textures made from bytes record where they were made when origin tracking is on. The harness's `--runtime-roots` adds the framework's statics, the shared array pools and an estimate of every object reached: the one-time 47 -> 52 MB step of live managed memory after the first visit is not reachable from any static field (the reached objects stay at 57.0 MB), and it does not grow after the second visit. Details: docs/BROWSER-PERFORMANCE.md, "Textures and live memory across visits".
