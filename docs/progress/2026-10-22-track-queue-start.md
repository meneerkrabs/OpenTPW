## The placement's queue start for the kart and water line tools (October 22, 2026)

A kart or water ride the player has just placed goes on into its queue tool once its circuit closes, as in tp.exe. A later close of the circuit, with no other placement's queue start pending, is decided by the click's modifiers, and help 204 is reached with the shipped rides. OpenTPW used to open the queue tool on every close of a ride with a queue, and every shipped kart and water ride has one. A line click whose ghost has a refused tile now ends the line tool and lays nothing, also when the line has a start ([TRACKS.md](../TRACKS.md), "Messages"). This closes the gap left open by the help 204 port of the same day.

- **The queue start.** A placement of a type with an entrance stores the record of its queue's start cell in `0x8186C0` (`0x52A050`, the cell in `0x7639B8`/`0x7639BC`). Four placement sites set it: `0x524DD7`, `0x525269`, `0x52544E` and the Move tool's `0x5258AC`. When a line closes the circuit, the handler tests it (`0x526F95`). While it is pending, the queue tool takes over at the stored cell, whatever the click held, and the handover zeroes it (`0x527056`). With none pending, exactly Ctrl keeps the line tool without a start (`0x527146`) and any other modifier word ends it. Other code zeroes it too:
  - the build tool's and the Move tool's click, before they place (`0x524B53`, `0x5253F3`). A click on a refused ghost never gets there: the placement preview `0x528A70` runs the object's cells through `0x532FC0(0x104)`, whose validator refusal sets the latch `0x816D48` (`0x533933`), and the click handler tests the latch before the mode dispatch (`0x524A63`), which sends modes 4 and 0x3B to `0x52765B`;
  - the Move tool's pick-up, a click in mode 0x33 (`0x525E5A`);
  - a path or queue commit, after its LayLine (`0x527483`);
  - the queue tool that follows any other ride's placement (`0x5252EA`), and the coaster tool's own handover to it (`0x526680`). (Since the original coaster flow, a coaster's own placement enters the queue tool too and consumes the start, so the coaster tool hands over only to a start another placement left pending.)

  The cross-reference list of `0x8186C0` has no other writer.
- **The port.** `Level.EnterPlacedTrackTool` opens the track tool of a placed kart or water ride and leaves the ride's queue start pending. `ParkHud.FinishPlacement` calls it. `Level.ContinueTrackTool` hands a line's close to the pending ride's queue tool and takes the start. With none pending, the close goes to the exactly-Ctrl rule. The clicks above drop the start:
  - `Level.ClickBuildTool`, the build and Move tools' click, now its own method, when the ghost is accepted (`Level.BuildGhostAllowed`, the rule the HUD's ghost already drew with);
  - `Level.BeginMove`;
  - a path or queue commit in `Level.ClickCellTool`. A click on a refused ghost commits nothing and keeps the start, and so does a line whose command the park refused before running it (`SegmentResult.CommandRefused`, set by the command writers). A command that threw while it ran keeps what it wrote, so it drops the start like a commit;
  - `Level.FinishCoasterTool`.

  The start is local tool state of the issuer, never a command, saved or hashed. It may belong to another ride than the circuit that closes, as in the original. A start whose ride was sold since is dropped: an OpenTPW guard, since its queue tool needs the ride.
- **The started-line refusal.** The kart and water line modes preview the line from the start (`0x52452E`: `0x53AAC0` with mode | 0x100). The preview walks the line tile by tile and stops at the first tile the ghost routine `0x5370E0` refuses: its chooser `0x539760` returns 1, and its money test at `0x539F95` counts too. The refused branch sets the latch (`0x537A1B` → `0x527940(1)`). The click handler tests that latch before the mode dispatch whether or not a start is set (`0x524A63`), and the mode table sends 0xB and 0x10 to `SetMode(0, 0)` (`0x5266A3`). `CellBuildTool.Click` therefore ends the line tool and lays nothing for a refused tile anywhere on the line, as it already did for the path and queue tools and for the line tool's first click. Before, it laid the line up to the refused tile, or up to the money.
- **What players notice.** Right after placing a kart or water ride nothing changes: closing its circuit goes on into its queue tool, Ctrl or not. Once that start is used up, or dropped by another placement, a Move pick-up or a queue line, a later close (through the ride window's track button, for example) no longer opens the queue tool. Exactly Ctrl keeps the line tool, any other click ends it, and the kept tool's next click gives the advisor's help 204. As in the original, the start a kart or water ride's placement left pending takes the next close to that ride's queue tool, whichever circuit closes. A line that crosses a blocked tile, or that the park cannot pay for in full, is not built at all, and the line tool ends with the refusal cue. The README and the website now say 236 of the 248 messages are spoken.
- **Documentation.**
  - UI-031's text (`UiApproximations.cs` and the docs/UI.md row) gives the line tools' handover with the pending start.
  - UI-031 also notes that the coaster tool's click, when its pass 0x81 returns 0 (`0x526525`), hands over to the queue tool only while a start is pending (`0x52656E`) and otherwise ends the tool (`0x5266BC`). What that pass stands for is still open, and OpenTPW's coaster flow differs, as UI-031 already records. No new APPROX ID.
  - `docs/TRACKS.md` ("Messages"), `docs/TRACK-LINE-CONTINUATION.md`, `docs/LIPS.md` and ADVISOR-SCAN.md drop the "not reached yet" notes.
- **Tests.**
  - `TrackAddOnLevelTests` (the new `TrackAddOnLevelTests.QueueStart.cs`), on the asset-free kart level:
    - a placed ride's close hands over to its queue whatever the close held (no modifier, exactly Ctrl, Ctrl+Shift), and the handover uses the start up;
    - with no start pending, a ride with a queue keeps the line tool for exactly Ctrl and ends it otherwise;
    - an accepted build click, a queue commit, a queue command that throws after a write, and the Move tool's pick-up each drop the start; a build click on a refused ghost, a refused queue click and a queue line whose command the park refuses (through the real command writer) keep it;
    - a kart ride the HUD places through the build click and its command (`ParkHud.OnObjectPlaced`, `AfterIssue`, `FinishPlacement`) gets its track tool with its start pending, and its close goes into the queue tool;
    - a line with a start across a queue cell, or across more tiles than the park can pay for, lays nothing, charges nothing, issues no line command and ends the tool.
  - `TheClickThatGivesTheKeptLineToolItsStartPostsHelp204` also runs for a ride with a queue.
  - `AudioRegisterRound2Tests.ARefusedTrackToolClickThroughTheHudPlaysTheRefusalCueAndNoTrackClick` also covers a line with a start: no track click 0xCE, and the refusal cue 0xAF on release.
  - `AFollowingQueueWinsOverExactlyCtrl` is replaced: the track button's line tool has no queue start pending.
  - Each part was taken out once to check that a test catches it. Without the start set at placement, the HUD's call of it or its deferred end of the placement, its use at the handover, any one of the three drops, the refused-ghost gate of the build click, the refused-click or refused-command exception (or with a command that threw counted as refused), or the started-line refusal, its own tests fail. With the old rule, which follows the queue on every close, eight tests fail.
