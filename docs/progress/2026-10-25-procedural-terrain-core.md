## The original's procedural terrain texturer, as a decoder and a byte-exact port (October 25, 2026)

Part of #829 (package E, steps E1 to E3). tp.exe's option PROCEDURALTEXTURING gives every terrain cell its own N × N ground texture, built from one file per theme, `terrain.wad/base.lnd`. OpenTPW did not read that file and draws one repeated texture per slot. This change adds the decoder, the texturer and the oracle evidence; nothing is drawn differently yet (the renderer wiring, the visible-cell cache, the option mapping and the shader are the next steps, after #834 which also touches `OriginalTerrain`).

- **`LndFile`** (`OpenTPW.Files`): version byte 3, the five (centre, width) blend parameters, the 384 × 344 weight grid at four samples per cell, and the three resolution sets (N = 64, 32, 16) of 13 images. The reader is strict and bounded and must end exactly at the file size; all four themes do. The layout is in [LND.md](../LND.md).
- **`ProceduralTerrainTexturer`**: `[BIN:TPW-EXE:0x0055F780]`'s head. Three layers (dirt, grass and foliage in the jungle) lerped by a ramp of detail map × weight 1, two masks, 16.16 forward-differenced weight planes, point-sampled windows `(N·x) % (w − N)`, per-16-texel run decisions (C, B, A, BA, CB, CA, CBA), the grey fallback for invalid cells, bottom-up rows. Pure CPU, deterministic, no allocation per cell.
  - **The three-layer quirk is kept.** `0x0055EAA0` never advances its weight 1 pointer, so all 16 texels of a three-layer run use the first texel's weight 1.
  - **Alpha is 0**, as the original writes it. A renderer must write 255 (OpenTPW's shader discards low alpha; the original's terrain pass is deduced to have no alpha test, since its cache textures carry alpha 0, but the render state of `0x56F670` is not traced); that is the shader step, not done here.
- **x86 oracle target X27** (`tools/ppc-analysis/oracle_x86`): the ramp `0x55E710`, the weight plane `0x55E780` and the build routine `0x55F780` run in the Unicorn sandbox on synthetic levels. The ramp agrees on 600 of 600 inputs, the weight plane on 500 of 500, the build on 48 of 48 cells that reach every run mode and the grey fallback; a reading without the quirk differs on 12 of the 48.
- **Real cells, byte for byte.** `terrain_golden.py` runs the original build routine on the shipped `base.lnd` of the four themes for 297 sampled cells (all sizes, corners and invalid cells included) and writes only their SHA-256 hashes into `ProceduralTerrainGolden.cs`. The C# texturer reproduces all 297. The earlier research had compared its Python model with the emulated routine on 33,820 cells with no mismatch. No original byte or image is committed.
- **Synthetic levels in CI** (`ProceduralTerrainSyntheticTests`): 27 levels from an LCG and fixed formulas (the same generator in Python and C#; not original data) with gradient weights, random ramps, every run mode, the grey fallback and N = 16, 32 and 64, 54 cells in all. tp.exe's routine ran on them in the oracle and their hashes are committed, so CI, without game data, checks the weight interpolation, general ramps, window offsets and N = 64.
- **With-data tests** (`ProceduralTerrainCorpusTests`): file identity and layout of all four themes (sizes, SHA-256, parameters, image sizes, the wrap padding of every image), every non-hole heightfield cell inside the grid is valid in the weight grid (the grid marks 6 to 68 holes valid as well), and the cell edges continue into each other (seam 13.7 against 12.7 inside a cell, jungle patch at N = 32), which fixes the orientation: texel columns along +x, buffer rows along +z.

Still open:
- Heightfield column 95 lies outside the 95 weight cells (the texturer refuses it); whether the original textures it procedurally or keeps its static texture is not settled.
- The extent of the original's procedural rectangle, and the texture pages, mipmaps and edge address mode of its cache textures, are not traced.
- The floor-art tail of `0x55F780` (rides and shops, package F) is not ported.
