## Original coaster placement flow (November 1, 2026)

Round 11 follow-up F2 ports the original's coaster flow (UI-031). Read statically in tp.exe (REA, `dis.py`); the Mac decomp only pointed to the code.

- **Placement.** A placed coaster takes the placement tail like every ride with an entrance: the queue start comes from `0x52A050` (`0x525264`, stored at `0x8186C0`), the tail calls `0x52F580(3, 0)` at `0x52529E` and clears the pending start at `0x5252EA`. The kart and water station line `0x525219..0x525256` is skipped for a coaster (`0x52FAF0 == 3`, test at `0x52521E`). The coaster tool (mode `0x15`, entry `0x497D20`) is never entered from the dispatcher `0x524960`. OpenTPW's `ParkHud.FinishPlacement` no longer enters the coaster tool: the queue tool opens, the coaster is not being edited and the log holds the placement alone.
- **Track tool entry.** `0x4988C0` asks `0x441910` (flag word `+0x3C`: bit 0 set, bit 1 clear means complete): an incomplete track enters `0x497D20` (`0x498947`, tool `0x15` via `0x46C580`, `0x46C350`, sub-mode 3 by `0x52FAD0`), a complete one `0x4474D0(thing, 1)`, the edit entry; neither calls the advisor help `0x486B00`, so the entry posts no advisor help (OpenTPW used to post `0x125`); the complete branch only sets the status text `0x4A2AA0(0xC)`, left unported under UI-031, and `0x441910` also needs the controller from `0x436860` to exist; the port opens the same panel for a complete and an incomplete track. The panel's own build button is not routed through `0x4988C0`: it calls `0x497D20` directly (`0x498337`) and posts help `0x125` (`0x498348`). Three routes lead in: the ride window's track button (`0x4AF200` to `0x4AF275`), a press on a marker cell of the coaster (the hover handler `0x486D90` maps map type `0x15` to cursor mode 6, switch `0x4875AE`, mode set at `0x48772B`; the click dispatcher's case 6, `0x487E56`, calls `0x4988C0` on the cell's owner thing at `0x487EEB`, opening no window) and the panel's own build button (control `0x1F`, `0x498333`, which calls `0x497D20` itself). The press enters the tool and its release is delivered to the new tool (`0x46C610` to `0x524960`), so on an incomplete track it is a build click. OpenTPW had the first and the third; the press on a marker cell is new (`Level.CoasterAtMarkerCell`).
- **Completion.** The coaster tool's click takes the pass `0x81` zero result to `0x526568` (`0x526514`), which hands over to the queue tool only while the queue start is pending (`0x52656E`, taken at `0x526680`); the placement consumed it, so the tool ends (`0x5266BC`). `Level.FinishCoasterTool` keeps the handover only for a pending start (`placedQueueStart`, a kart or water ride's): the global is cleared by the build, Move, pick-up and path or queue clicks (`0x524B53`, `0x5253F3`, `0x525E5A`, `0x527483`, the same points as OpenTPW) and not by a tool's exit, and a coaster's own placement consumed it at `0x5252EA` (`0x52FAF0` returns 3 for a coaster: the build tool's activation `0x46D653` stores the type's `+0x9C` through `0x52FAD0` while `0x8187F8` holds the item; `0x525296` zeroes `0x820A8C`, whose only writers of 1 are line-tool code, so the clear is reached whenever the start differs from the two locals compared at `0x5252A9`/`0x5252B9`).
- **Co-op and determinism.** The claim stays at the tool entry (`BeginCoasterToolEntry`, so now at the track button or the click on the coaster); the entry stays a command of its own (`BeginCoasterTool` after its claim), one tool per peer and the `HostToolStarts` fence are kept. Old command logs that hold a placement followed by `BeginCoasterTool` still replay (test). No pins move.
- **UI-031 (narrowed).** The coaster parts are ported; left: the status texts of the mode 6 hover (help `0xB`) and of the tool entry (`0x4A2AA0` with `0xC`), the path-start queue cell (`0x5259CF`) and which OpenTPW placements end there.
