## UI-003 button state selection read (November 8, 2026)

Settled the register's open question the other way round: a model button *does* drive the first-child chain index. The base constructor `0x6597B0` starts every control's `+0xA` and `+0xC` at zero (`0x659814`, `0x65981D`); `0x476E80` writes `+0xC` from the message's word `+4` under bit `0x1` and `+0xA` from the message's word `+0xA` under bit `0x80000`; and the button class sends bit `0x1` with the `0x668820` state to the model control at `[button+0x98]` (`0x668A58`, `0x668C55`, `0x668D06`, whose flag word starts at one at `0x668CB8`). That control's slot 3, `0x476F10`, forwards flags and message to `0x476E80` at `0x476F5D`. The model attach sends flag `0x57` (bit `0x1`, index 0) at `0x65D14E` and the sibling slot-3 overrides `0x477310`/`0x477640` pass the flags through, so every model control is driven this way. The only site that sends bit `0x80000` as a control message is `0x66160C`, which nothing references; no other site sends that bit as a control message, and no writer of `+0xA` besides the constructor and `0x476EAE` was found. The base therefore stays zero and the button state is the chain index, which is what `UiModel.TryGetState` already does.

The `0x4C000` send of the applier `0x668AD3` is a different message to a different control: `[button+0x9C]`, a text control (vtable `0x6FF320`, slot 3 `0x48FC40`), so it sets the label's per-state appearance rather than the model. Its table `0x668BD4` holds three distinct bodies: states 0 and 2 emit two zero words and the dword at `+0x14C`, states 3 and 5 the button's bytes `+0x158`/`+0x159` and the dword at `+0x154`, state 4 the byte `+0x158` plus one, `+0x159` and `+0x14C`; state 1 and any state above five send the zero message word without any descriptor field. `0x48FC40` carries the descriptor's `+0xA` to text `+0xDE`, `+0xC` to `+0xE0` and `+0x10` to `+0x48`, the label's RGBA colour, decomposed at `0x48FD0A..0x48FD44`.

The register entry now records that reading and narrows the ID to its true residual, widened by one finding: a button's own sends carry the state (0 to 5), but the base-class frame setter `0x65D3A3` sends bit `0x1` with the caller's own word from 32 call sites, some computed or script-supplied, and whether any of those targets a button is unchecked. So a control asked for a state past its model's chain keeps its first frame here where tp.exe draws nothing, and whether a shipped button ever asks for such a state is not established. No runtime behaviour changes, no APPROX ID is added or retired, and no save or determinism data moves.
