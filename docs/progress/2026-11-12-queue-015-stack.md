## QUEUE-015: what the queue tool's stack actually decides (November 12, 2026)

The entry's residual named three things: the Move pick-up's stack copy and second walk, the per-click select re-map, and the tool entries' starting stack. Reading the executable narrows all three, and two of them turn out not to matter.

The stack at `0x820A8C` is read by exactly three things: its count getter `0x52FBE0` — the "click on the start with more than one point" test — Back `0x52FE50`, and the copy `0x52FC30`. That copy's four globals `0x818D98`, `0x818D9C`, `0x820A90` and `0x820A94` are referenced only inside `0x52FC30` itself, and the return byte `0x81B14C` is written at `0x48D00E` and read nowhere. The second walk at `0x527F9A` resets the count and refills it, so the first walk's stack is discarded regardless.

So neither the copy nor an unseeded stack can change an acceptance, a refusal, a cell type or a link byte. What is genuinely left is narrower: a ride placement enters mode 3 with the stack the placement click left, at least two points (`0x5259AE..0x525A06`), so clicking the start cell ends the tool there, while this port starts a queue edit with one point and lays a one-cell line. The per-click select `0x5276D0` is real for the track tools' selection and orientation globals but changes no queue decision, and the Move gesture itself belongs to UI-024.

The declaration now says all of that, so the next reader does not go looking for a behavioural gap in dead state.
