## Direct3D 11: whole-buffer writes into dynamic buffers (November 21, 2026)

Issue #829's newest report: after an NVIDIA driver update on Windows the park view flickered. Frame-by-frame, the reporter's video shows the bottom help box ("Left-click to build a path" / "to extend this path") vanishing and coming back from one frame to the next while the camera and the cursor stand still, sometimes leaving a thin dark line. A probe through the ordered pointer pipeline kept the help id (441) steady over frames with, without and with empty pointer events, so the help state was not what changed; the draw was.

The likely cause is how dynamic buffers were written on Direct3D 11. Almost every per-frame upload (the interface's vertices, the text, guests, staff, thoughts, balloons, litter, particles, weather, sky, pools, the per-draw uniform block of every material) writes only part of a `BufferUsage.Dynamic` buffer. Veldrid 4.9 maps a dynamic buffer only when the update covers all of it (`D3D11GraphicsDevice.UpdateBufferCore`, `D3D11CommandList.UpdateBufferCore`); a partial update goes through a staging buffer and `CopySubresourceRegion` into the dynamic buffer. The D3D11_USAGE reference ("Resource Usage Restrictions") gives `D3D11_USAGE_DYNAMIC` no GPU write access and documents copies only to and from staging resources or between resources of the same usage; `Map` is the intended way to write a dynamic buffer. A staging-to-dynamic copy is outside those paths, so its result is up to the driver; older drivers evidently kept it.

`DynamicBufferUpload.Update` now does every buffer write. On Direct3D 11 a partial write into a dynamic buffer is widened to the whole buffer from a scratch copy, which Veldrid writes with `Map(WRITE_DISCARD)`, the path the usage is meant for. Metal, Vulkan and the browser's WebGL keep the caller's byte count, so nothing changes there. A source contract test keeps any new `.UpdateBuffer(` call (generic ones included) out of `source/OpenTPW`, `OpenTPW.Common` and `OpenTPW.ModKit` outside the helper.

The same issue's lightning report (the island select flash is "a negative picture") needs no change. tp.exe draws the flash quad with state `0x9A1` (`0x57ED75`), and its state setter `0x5679B0` passes source blend INVDESTCOLOR and destination blend ZERO to the device with no capability fallback. The only override is the anaglyph pass's additive blend (`0x57714E`..`0x57717C`), which normal play never uses. A recording of the original PC v2.0 shows the same one-frame negative of the Halloween island.

Verified: the new `DynamicBufferUploadTests` and the ordered pointer, UI and model tests (84 passed), the browser build against the WebGL shim, and the five native smokes on Metal. Not verified: a run on Direct3D 11 with an NVIDIA driver; there is no Windows machine with that driver here, so the reporter's check decides whether this was the flicker. Still open: the Veldrid.ImGui package's renderer (the editor overlay and the first-run setup wizard) writes its own dynamic buffers partially and is not routed through the helper. No APPROX ID; the D3D11 rule is a platform contract, not a game rule.
